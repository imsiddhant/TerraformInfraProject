Overview

This project automates the provisioning of all necessary AWS infrastructure for a multi-tier web application using Terraform. It sets up networking, compute resources, a relational database, and CloudWatch monitoring — all reproducible from source code.

🌐

Networking

VPC, public/private subnets across 2 AZs, IGW, route tables, and security groups.

⚙️

Compute

Auto Scaling Group of EC2 instances behind an Application Load Balancer.

🗄️

Database

RDS MySQL 8.0 in private subnets with a dedicated security group.

📊

Monitoring

CloudWatch alarms for CPU and storage, with SNS email notifications.

Why this project

Manually provisioning cloud infrastructure is time-consuming, error-prone, and hard to reproduce across environments. This project solves that by fully automating the deployment of a production-ready stack on AWS:

  • The entire stack spins up or tears down with terraform apply / terraform destroy
  • All infrastructure is version-controlled and reviewable via pull requests
  • Modular design makes it easy to extend or reuse individual components
  • Multi-AZ deployment and auto scaling provide production-grade resilience
  • State is stored in Terraform Cloud for team-safe remote operations

Quick start

  1. Clone the repository
    git clone https://github.com/<your-username>/TerraformInfraProject.git
cd TerraformInfraProject
  2. Customize variables (optional)
    Edit the variable defaults in each module's variables.tf, or pass them via a terraform.tfvars file.
  3. Initialize Terraform
    terraform init
  4. Preview the execution plan
    terraform plan
  5. Apply and provision
    terraform apply
    Terraform will prompt for confirmation. Type yes to proceed.
  6. Tear down (when done)
    terraform destroy
ℹ️

State is stored in Terraform Cloud (organization: geekat7, workspace: InfraProject). Make sure you are authenticated with terraform login before running terraform init.

Traffic flow

  1. Users send HTTP requests to the ALB DNS name on port 80.
  2. The ALB forwards traffic to healthy EC2 targets in the target group.
  3. EC2 instances (Apache + PHP) handle the request and query RDS MySQL in the private subnets.
  4. CloudWatch monitors CPU (EC2) and free storage (RDS), sending SNS email alerts on threshold breaches.

User-data script (app.sh)

The EC2 instances run app.sh on first boot, which:

  • Updates system packages via dnf
  • Installs Apache httpd, PHP, php-mysqli, and MariaDB client
  • Starts and enables the httpd service
  • Writes /var/www/inc/dbinfo.inc with RDS connection parameters
  • Creates a testdatabase.php page that reads/writes an EMPLOYEES table
💡

After provisioning, access the demo app at the ALB DNS name output by terraform output on path /testdatabase.php.

Network security

The RDS security group allows inbound traffic on port 3306 exclusively from the EC2 security group (FromALBOnly). No direct internet access is possible.

⚠️

The database username and password are currently hardcoded. For production use, migrate these to AWS Secrets Manager or Terraform input variables with a .tfvars file that is not committed to version control.

SNS notifications

Both alarms publish to a single SNS topic (default-sns-topic). An email subscription is created automatically. The subscriber must confirm the subscription via the confirmation email sent by AWS after apply.

Security notes

⚠️

This project contains hardcoded secrets for demonstration purposes. Do not use it in production without addressing the items below.

Known issues & recommendations

IssueRecommendation
Hardcoded RDS username & passwordUse AWS Secrets Manager and data "aws_secretsmanager_secret_version"
Hardcoded SNS email addressMove to a Terraform input variable or .tfvars file
EC2 in public subnetsMove EC2 to private subnets; use a NAT Gateway for outbound internet access
No HTTPS on ALBAdd an HTTPS listener with an ACM certificate
ASG max = 1Increase max capacity and configure scaling policies for production workloads
